# x-quality — 代码质量宪法

## 核心原则

**每一行代码都要有一个当前存在的理由。** 说不出理由的代码，删掉比留下便宜。

这份标准是**同一份**：写的人用它自检，审的人用它复核，测的人用它判断可测性。标准不一致 = 没有标准。

## 何时不用

- 你在评估架构（接缝、抽象层次、职责划分）→ 不归这份标准管，它只管单点代码。
- 你在做威胁建模或可达性分析 → 不归这份标准管。
- 项目是原型或一次性脚本、明确不打算维护 → 说明"不适用"，不要硬套 14 条。

## 两层判定

**机械层**：项目自带的类型检查、lint、死代码检测、重复检测、复杂度检测，必须**零新增告警**。

项目没有这些工具时，用每条规则的"判定方法"人工判定，并在 artifact 里写明"无工具，人工判定"——不许因为没工具就跳过。

**判断层**：以下 14 条。复核时引用编号（`QS-07`），不写散文。

## 规则

### QS-01 死代码 = 0

**判定**：未被引用的导出、私有函数、参数、依赖；不可达分支；被注释掉的代码块；`throw new Error('not implemented')` 的占位 API；只有测试引用的生产代码。

**通过**：先判这个符号在不在对外面上。**对外面** = 出现在 HTTP 响应字段、包导出、外部系统直读的表列、配置文件键、对外事件消息字段。

- **不在对外面**：四项都排除才删——直接调用、反射或计算键动态读取、框架/目录约定、在途工作。要保留就写进 `02-design.md` 的"不建清单"，而不是留在代码里。
- **在对外面**：零引用不是删除依据。写清"谁会读它"的 `未验证：` 项，交给人决定，不自行删。

**删之前先说出它为什么被加进来**（git log / 调用方 / 注释）。说不出 = 先查清再删。

### QS-02 抽象必须有 ≥2 个真实调用方

**判定**：每个 interface、基类、策略、工厂、包装层，数一下**当前**调用方。≤1 个 → 直接调用，别抽象。

**删除测试**：删掉这层抽象，复杂度是集中了，还是只是搬了个地方？只是搬了个地方 = 这层抽象不成立。

**通过**：≥2 个真实消费者，或抽象边界由外部契约强制（框架要求、序列化格式、第三方接口）。

### QS-03 领域字面量必须有命名来源

**判定**：数字、字符串、URL、超时、阈值、状态码、错误文案，凡是有业务含义的，必须来自命名常量、配置项或已验证的输入，不得直接写在调用处。

**通过**：改这个值只需要改一处；同一个含义在全仓库只有一处定义。

### QS-04 默认值唯一来源

**判定**：同一个默认值（超时、上限、重试次数）在几处出现？参数默认值、配置默认值、文档、测试夹具各写一遍 = 四份真相。

**通过**：默认值只有一处定义，其余全部引用它。

### QS-05 禁止 import 时副作用与全局可变状态

**判定**：模块顶层是否读环境变量、开定时器、连数据库、注册全局钩子、建可变单例？

**通过**：依赖从参数或初始化函数注入；模块导入本身不改变任何外部状态。

### QS-06 规模预算

**判定**：函数体超过约 40 行、嵌套超过 3 层、单文件超过约 300 行、参数超过 4 个 → 需要理由。

**通过**：超预算处有明确拆分理由，或已拆分。数字是预算不是法律——超了要能解释，不是超了就违规。

### QS-07 错误不得静默

**判定**：空 catch；catch 后只打日志继续跑；把异常转成 `null` / `false` 让调用方猜；错误类型用字符串匹配。

**通过**：错误要么向上传播，要么在边界转成有类型的失败结果；每个 catch 都能回答"谁在处理这个失败"。

### QS-08 命名使用领域词汇

**判定**：变量名是 `data` / `info` / `manager` / `helper` / `utils` 这类无信息词？命名与项目术语表（`GLOSSARY.md`）冲突？

**通过**：命名与领域词汇一致；读名字能知道它是什么，不用读实现。

### QS-09 测试在公共接缝、期望值独立

**判定**：测试是否 mock 内部协作者、调用私有方法、断言实现细节？期望值是否由被测代码的同一套算法算出（同义反复）？

**通过**：只测公共边界行为；期望值来自独立来源（手算样例、规格原文、已知正确字面量）；重构实现而行为不变时，测试不该红。

### QS-10 配置必须有消费者，开关必须有移除条件

**判定**：新增的配置项、环境变量、特性开关，有没有当前读它的代码？开关有没有写明的移除时间或移除条件？

**通过**：每个配置有消费者且被校验；每个开关写明"何时删"。

### QS-11 注释解释为什么

**判定**：注释在复述代码（"// 加一"），还是在解释取舍、约束、外部系统的失败方式？

**通过**：注释只出现在"读代码看不出来的原因"处；被注释掉的代码一律删除（历史在版本控制里）。

### QS-12 范围纪律

**判定**：diff 里有没有任务没要求的重构、格式化、顺手改名、"反正都要改"？

**通过**：diff 里每一处改动都能对应到 `00-brief.md` 的一条要求；无关改动拆出去。

### QS-13 依赖注入而非内部构造

**判定**：函数内部直接 `new` 出时间源、随机源、HTTP 客户端、数据库连接、日志器？

**通过**：外部依赖从边界传入，测试里可替换。不可测的代码等于没测。

### QS-14 不可逆决策必须留痕

**判定**：选型、数据格式、公共契约、删除公开 API —— 有没有记录"当时为什么这么选、否决了什么"？

**通过**：有 ADR 或 `02-design.md` 的决策段，且写了**推翻条件**（什么情况下这个决定要重选）。写不出推翻条件 = 还没想清适用边界；只记"当时为什么这么选"的决策永不过期，三年后没人敢动。

## 证据格式（唯一格式，所有角色共用）

每条结论后面直接跟"我怎么知道的"。三种形态，按可得性选：

| 形态 | 写法 | 例 |
|---|---|---|
| 命令型 | `<命令> → <关键输出>` | `du -sh node_modules → 412M` |
| 文件型 | `<路径>:<行号> → <原文片段>` | `src/pricing.ts:14 → class PercentageDiscountStrategy` |
| 无法取证 | `未验证：<缺什么>` | `未验证：默认超时的来源，配置中无该字段` |

**禁止三种写法：**

- 只写结论不写来源：「测试已通过」「已检查」「应该没问题」
- 只写来源不写内容：「见 xxx.json」「[A]」
- **用代号代替内容**：`[A]` / `[B]` / `[C]` / ✅ / 任何等级符号 —— 代号需要图例，图例本身就是黑话

判据：**别人照着你写的命令敲一遍，或打开你写的行号看一眼，能得到同样的东西。** 做不到就不是证据。

## 结论优先（唯一写法，所有角色共用）

正文只写结论。**推导过程不进正文。**

写 `A → C`，不写 `A → B → C`。B 是证据，附在结论后面。

- 反例：「先看了 pricing，发现有 3 个策略，又查了调用方，发现只有 1 处调用，所以另 2 个是死代码。」
- 正例：「`pricing.ts` 有 2 个策略零调用方（`pricing.ts:14` → 3 个实现；`grep -rn "new .*Strategy"` → 只有 1 处实例化）。」

只有两种情况可以把中间环节写进正文：

1. **B 本身就是交付物** —— 调用链、攻击路径、回滚步骤、失败模式序列。这些的中间步骤就是结果。
2. **跳过 B 结论无法核验** —— 此时 B 必须写成可验证的形式，不是叙述。

判据：把正文里所有「我先」「然后」「接着」「后来」「顺便」删掉，句子仍然成立。删掉就读不懂，说明结论还没成形——回去重写结论，不是把过程补回来。

报告长度由**结论数量**决定，不由**工作步骤数量**决定。做了 40 步得出 1 个结论，就写 1 个结论 + 1 条证据。

## 复核输出格式

复核者只输出这个结构，不写散文：

```
QS-01 PASS
QS-02 FAIL  src/pricing.ts:14 → PercentageDiscountStrategy 只有 1 个调用方
QS-03 FAIL  src/pricing.ts:41 → 100 为内联字面量，应来自 CURRENCY_SCALE
QS-05 FAIL  src/middleware/rateLimit.ts:19 → 模块顶层读 env 且建可变 Map
QS-07 PASS
...
结论：FAIL（3 项）→ 打回产出方
```

每条 FAIL 必须带证据（格式见上）。给不出证据的 FAIL 不成立。

## 借口与回应

| 借口 | 现实 |
|---|---|
| "以后可能会用到" | 以后用到时再写。现在留着 = 现在就要维护、就要测、就要被误用 |
| "先留着，注释掉方便回滚" | 回滚靠版本控制，不靠注释 |
| "抽出来以后好复用" | 数调用方。1 个就是过度设计 |
| "就一个数字，没必要提常量" | 那它出现在第二处时谁来改？ |
| "加个开关更安全" | 没有移除条件的开关是永久债务 |
| "这是框架要求的写法" | 指出框架文档位置；指不出就是在给有缺陷的设计找理由 |
| "测试里 mock 内部类更方便" | 那测的是实现，不是行为。重构就红 = 假测试 |
| "TODO 先放着，下个迭代做" | 未实现的 API 上线 = 死代码 + 线上隐患。要就现在做，不要就删 |
| "类型报错，加个 any 先过" | 类型逃逸是把错误从编译期推迟到生产环境 |
| "代码风格问题不重要" | 风格不致命，但"顺手重构"会让评审看不见真正的改动 |

## 红旗

- 新增文件但没有任何调用方
- 同一个数字在 diff 里出现两次
- 出现了 `Manager` / `Helper` / `Util` 结尾的新类型
- 空 catch、`catch (e) {}`、`catch { return null }`
- 模块顶层 `setInterval` / 读环境变量 / 全局单例
- 注释掉的代码块、`// TODO: implement`
- 测试里出现 `expect(f(a,b)).toBe(a+b)` 这类同义反复
- diff 里出现与需求无关的文件
