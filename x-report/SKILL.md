# x-report — 让人能做决定的产物形状

## 核心原则

**结构不选模板，只回答一个问题：读者看完要做什么。** 说不出这个决定，这篇东西不是汇报，是记录。

## 判断入口：先定决定，再定顺序

| 读者要做的决定 | 按序回答（缺一条即未完成） |
|---|---|
| 发 / 不发 / 回滚 | 结论 → 影响范围（字段按该产物的输出格式，不许留空）→ 修复路径（含耗时）→ 残余风险（含怎么发现它复发） |
| 选 A 还是 B | 推荐 → 被否方案为何不够 → 代价（谁要改什么）→ 什么条件下该翻案 |
| 会不会再犯 | 结论 → 时间线（只留决策点）→ 根因 → 已改 / 未改（未改的写触发条件） |
| 能不能上（安全） | 能否被利用 → 路径（每步落 `文件:行 → 原文`）→ 影响面 → 修法与残余风险对比 |
| 接手的人下一步做什么 | 已完成 → 在跑 → 卡点 → 下一件事 |

**按决定查表，不按场景名查表。** 同一个决定的两种叫法（线上事故、bug 上报）用同一行，不许造第二套顺序。

## 三条判定

1. **决定必须单一且能命名。** 读者要做的决定不止一个 → 拆成两篇；说不出决定 → 用分面清单按维度平铺，不套序列。
2. **序列内每一问都要能落证据。** 按 `x-quality` 的证据格式写：`命令 → 输出`、`文件:行 → 原文`、`未验证：<缺什么>`。落不到的那一问就是没做，不许用形容词补位。
3. **结论在前，过程在后。** 按 `x-quality` 的「结论优先」写：正文只写 A → C，中间环节 B 进证据链。序列的第一问本身就是结论。

## 何时不用

- 读者只需判断对错、不需做决定（同行技术评审、代码走查）→ 分面清单更适合。
- 纯记录（变更清单、日志、待办）→ 按时间或结构平铺。
- 一屏内、只有一个结论 → 直接说结论，套序列是增加摩擦。

## 常见失败

| 写法 | 为什么不算 |
|---|---|
| 背景铺垫，结论放最后 | 读者要走完全程才知道要不要读，决定被延迟了 |
| 「影响范围：接口层」 | 没有路径、比例、用户、依赖，这一问等于没答 |
| 「风险较低」 | 没有残余风险和检测方式，读者无法据此决定 |
| 四问里挑三问答 | 缺的往往是读者真正要的那一问（通常是残余风险） |
